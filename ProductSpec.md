## 1. Product Summary

Blocks Localization is the translation-management service of the SELISE Blocks platform. It gives a team one place to collect every piece of user-facing UI text for the apps they build on Blocks, store each text as a named **key**, translate that key into any number of **languages**, and deliver those translations to the running apps.

Translations are produced three ways:

1. **Typed by hand** — an editor enters each language's value directly.
2. **Generated by AI** — an assistant service (a ChatGPT-style completion endpoint, configured via `AiCompletionUrl` + `ChatGptTemperature`) fills missing values from the default-language source text, steered by an optional glossary of preferred terms.
3. **Round-tripped through files** — keys are exported to a downloadable file (JSON / XLSX / CSV) for offline translation and re-imported.

When translations are ready, an editor **publishes** them, which compiles a JSON dictionary (a "UILM file") per module per language that consuming apps read at runtime. A configurable outbound **webhook** can also notify an external system that new translations are live.

The product is **project-scoped and multi-tenant**: it renders inside the Blocks console shell (reusing `@seliseblocks/blocks-kit` layout, guards, and dashboard routing), every backend operation is scoped to the current project via `BlocksContext.GetContext().TenantId`, authentication is OIDC through blocks-iam, and every mutating endpoint is guarded by a `blocks-localization::…` permission. It runs as a .NET web host (`net10.0`) serving a React + Vite SPA, plus a separate **Worker** process that runs long operations (translate, publish, import, export, migration) off `eurolm_*` message queues with in-app completion notifications.

**Headline value (Open / undecided — Q-C1):** the code supports all of "centralize scattered translation files," "ship in more languages faster via AI," and "keep terminology consistent via glossaries." Which is the *primary* positioning is not decided.

## 2. Personas & Jobs-to-be-Done

The tool lives inside the project console next to developer/admin settings, yet its core daily work — editing wording and running translations — is a content/translation job. The intended **primary day-to-day persona is not formalized** (Open / undecided — Q-B1, Q-D5).

| Persona | In the product? | Jobs-to-be-done |
|---|---|---|
| **App developer** (building on Blocks) | Yes | Create **Modules** to group keys by app/area; add **Keys** whose `KeyName` matches the lookup id in app code, with optional **Context** and **Routes**; bulk-**import** an existing translation file to seed keys; wire the app to **consume** the published JSON dictionary at runtime; optionally configure the **webhook**. |
| **Project / tenant administrator** | Yes | Manage the **language set** and choose the **default (source) language**; configure the webhook endpoint + secret; trigger **Publish Changes**; review the **Timeline/Logs** and perform **rollback**; govern who can edit/translate/publish/delete via IAM permissions; promote translations between projects via environment migration. |
| **Translator / content manager** | **Not a formal persona** | The actual hands-on editor: edits per-language values, runs AI auto-translate, curates glossaries, and handles the offline file round-trip. Today this work is split across the developer and admin surfaces; there is no dedicated translator role or simplified translator view. (Open / undecided — Q-B1, Q-D5.) |
| **End user** (of an app built on Blocks) | No — indirect only | Never opens Blocks Localization. Experiences only the *output*: the app shows UI text in their language because it pulled the published dictionary. If a key has no value for their language, the placeholder `[ KEY MISSING ]` is emitted (whether that is an acceptable user-facing fallback is Open / undecided — Q-A4). |

## 5. Key User Flows

### Flow A — Set up a project's localization (App developer / Admin)
1. Open the project in the Blocks console; the localization menu appears (**Overview, Translations, Modules, Glossary, Configuration, Environments**).
2. **Configuration** (`services/configure`): add languages and mark one **default (source)** → `Language/Save`, `Language/SetDefault`.
3. **Modules** (`services/modules`): create a module per app/area → `Module/Save`.
4. **Translations → New Key** (`services/language/translations/new-key`): enter `KeyName`, pick the module, add optional Context/Routes, type per-language values → `Key/Save` (or `SaveKeys` for bulk). Alternatively **Import** a `.csv`/`.xlsx`/`.json` file to seed keys.

### Flow B — Translate (Translator / Content manager)
1. In the **Translations** table pick a key → **Translate**, or select several, or "translate all" untranslated → `Key/TranslateKey | TranslateKeys | TranslateAll`.
2. The request is queued; a worker calls `AssistantService`, which builds the prompt from the default-language value + merged glossary tiers (global → module → key, de-duplicated) and asks the AI for each missing language's value, then saves and writes timeline entries.
3. A human can **edit** any value inline → `Key/Save`. **Note:** no review/approval gate is enforced before publish (Q-B2).
4. Optionally curate the **Glossary** (`services/glossary`) so future AI runs use preferred terms.

### Flow C — Publish and consume (Admin → App)
1. Click **Publish Changes** → `Key/GenerateUilmFile` (no `ModuleId` ⇒ all modules).
2. The worker builds one JSON file per module per language (`{ keyName: value }`, `[ KEY MISSING ]` where absent), replaces the old files, increments generation history, and fires the webhook + an "Extension Sync"/completion notification.
3. The consuming app fetches its dictionary at runtime via `Key/GetUilmFile?projectKey=…&module=…&language=…`.
   - **Side path:** saving a key marked `ShouldPublish` auto-regenerates that module's file without an explicit Publish click (Q-B4).

### Flow D — Offline translation round-trip (App developer + external translator)
1. **Export** keys → choose format (**JSON / XLSX / CSV** in the current UI) and languages → `Key/UilmExport`.
2. The worker writes the file to storage; it appears under **Export History** (`Key/GetUilmExportedFiles`) to download.
3. A translator edits offline, then **Import** uploads it (`.csv`/`.xlsx`/`.json`) → `Key/UilmImport`; the worker merges values (existing keys updated, new keys added; modules not replaced).
   - **Gap:** the backend can also handle XLF/XLIFF, but XLF is currently disabled in the export list and absent from the import allow-list (Q-B7).

### Flow E — Audit & rollback (Admin)
1. Open **Logs** (`services/language/logs`) → `Key/GetLocalizationTimeline` (operation overview) and `Key/GetTimeline` (per key) / `GetTimelineByOperationId`.
2. To undo a bad change, **rollback** a key to a previous state → `Key/RollBack`.

### Flow F — Promote across environments (Admin / platform)
1. An `EnvironmentDataMigrationEvent` (source project → target project, optional overwrite) is processed by `EuroLMEnvironmentDataMigrationEventConsumer`, which copies modules first, then keys, and notifies on completion.
2. An **Environments** nav item exists, but the exact in-product trigger for a migration was not found in this repo — treat the invocation surface as Open (Q-C4, Q-D3).

## 6. UX Principles & Default Behaviours

These describe how the product behaves today; several are candidates for a deliberate decision (flagged).

- **Project-scoped by default.** Everything the user sees and every write is bound to the current project (`TenantId`); there is no cross-project view except the (undecided) migration/environments path.
- **Console-native.** The product reuses the blocks-kit console shell, guards, and dashboard route, so navigation, project switching, and auth feel identical to the rest of Blocks.
- **Permission-gated writes; lighter reads.** Every mutation carries a `blocks-localization::…` permission; a few read/timeline/suggestion endpoints are only `[Authorize]`. There is **no translator-only role** that permits edit/translate but forbids publish/delete (candidate decision — Q-D5).
- **Asynchronous heavy work with notifications.** Translate/publish/import/export/migrate return immediately and complete on the worker, surfacing an in-app notification. The UI should treat these as eventually-consistent.
- **AI as a first-draft assistant.** AI fills *missing* values from the source language and is glossary-steered; output is editable and is **not** gated by a review step. Whether AI output may go live directly is a candidate decision (Q-B2, Q-C2).
- **Glossary precedence.** When translating, glossaries merge global → module → key and de-duplicate by id, so more specific tiers supplement (not silently override) global terms.
- **Two publish triggers coexist.** A deliberate all-modules "Publish Changes" and an implicit per-module auto-publish on `ShouldPublish` save. The intended default (deliberate-only vs. allow implicit) is a candidate decision (Q-B4).
- **Two delivery paths coexist.** Apps *pull* the compiled JSON file; a webhook can *push* a change notification. The standard path is undecided (Q-B3).
- **Missing-translation fallback is a visible placeholder.** Absent values render as `[ KEY MISSING ]` rather than falling back to the source language; whether this is acceptable in production is a candidate decision (Q-A4).
- **Modules have no delete.** Module creation/update exists but deletion is intentionally not exposed (commented out) — treat modules as durable groupings.

## 7. Functional Requirements & Acceptance Criteria

### FR-1 Language management
- **Given** an admin with `language::save`, **when** they add a language, **then** it is stored for the project and becomes available for keys and translation.
- **Given** an admin with `language::setdefault`, **when** they set a default language, **then** that language is marked `IsDefault` and is used as the AI translation *source*.
- **Given** a language in use, **when** an admin with `language::delete` deletes it, **then** it is removed from the project's language set.
- **Open:** whether exactly one default must always exist (Q-A5).

### FR-2 Keys & resources
- **Given** a user with `key::save`, **when** they save a key with `KeyName`, `ModuleId`, and per-language `Resources`, **then** the key is created/updated and a timeline entry is written under an operation id.
- **Given** a bulk save (`key::savekeys`), **when** multiple keys are saved, **then** they share one operation id in the timeline.
- **Given** a key marked to publish, **when** it is saved, **then** UILM regeneration for its module is queued automatically (auto-publish — see Q-B4).
- **Given** a search (`key::gets`), **when** filters (module / translation status / missing languages / date range) are applied, **then** a paged, filtered key list is returned.

### FR-3 AI auto-translation
- **Given** a key with a default-language value and missing target values, **when** a user with the relevant `key::translate*` permission runs translate, **then** the request is queued and the worker calls the AI completion service.
- **Given** glossaries at global/module/key tiers, **when** a translation prompt is built, **then** they are merged, de-duplicated, and injected as glossary context.
- **Given** the AI returns empty, **when** translation runs, **then** it retries up to 3 times before failing.
- **Given** AI output is produced, **then** it is saved as the key's value with **no enforced human-review gate** (Q-B2).

### FR-4 Publish & runtime consumption
- **Given** a user with `key::generateuilmfile`, **when** they publish with no `ModuleId`, **then** files are generated for **all** modules; with a `ModuleId`, only that module.
- **Given** publish completes, **then** old files are replaced, a generation-history version is recorded, and the webhook + a completion/Extension-Sync notification fire.
- **Given** a published module+language, **when** a consuming app calls `Key/GetUilmFile?projectKey&module&language`, **then** it receives a JSON `{ keyName: value }` dictionary, with `[ KEY MISSING ]` for absent values.

### FR-5 Import / Export
- **Given** a user with `key::uilmexport`, **when** they export selected modules/languages in JSON/XLSX/CSV, **then** a file is generated to storage and listed in Export History.
- **Given** a user with `key::uilmimport`, **when** they import a `.csv`/`.xlsx`/`.json` file, **then** existing keys are updated, new keys added, removed keys ignored, and modules are not replaced.
- **Open:** XLF/XLIFF export and import are not exposed in the current UI despite backend support (Q-B7).

### FR-6 History & rollback
- **Given** any create/save/delete/translate/import/publish, **then** a timeline entry is written, grouped by operation id.
- **Given** a key with prior history, **when** a user with `key::rollback` rolls it back, **then** the key is reverted to the selected prior state.

### FR-7 Webhook configuration
- **Given** a user with `config::savewebhook`, **when** they save a webhook (`Url`, `ContentType`, secret `HeaderKey`+`Secret`, `IsDisabled`), **then** it is stored and invoked on generate/translate/import unless disabled.

### FR-8 Access control
- **Given** the IAM seed is applied, **then** 27 `blocks-localization::…` permissions (ResourceGroup `localization`) exist and each guards its endpoint.
- **Open:** no distinct translator role (edit/translate but not publish/delete) is defined (Q-D5).

### FR-9 Environment migration
- **Given** an `EnvironmentDataMigrationEvent` (source → target project, optional overwrite), **when** processed, **then** modules are copied first, then keys, into the target project, with a completion notification.
- **Open:** the in-product trigger/UI for migration is undecided (Q-C4, Q-D3).

## 8. Out of Scope / Roadmap

- **Self-contained data store (by design today).** Blocks Localization manages its own MongoDB collections (keys, languages, modules, glossaries, timelines, generated/exported files, webhook) directly, rather than through the blocks-data gateway. It depends on a storage driver only for file export/import. Whether this stays self-contained long-term is Open (Q-D1).
- **Own change history (business audit, not platform monitoring).** The Timeline/Logs feature is a business-level audit trail with rollback, distinct from blocks-monitor. Whether it eventually rolls up into platform audit tooling is Open (Q-D2).
- **XLF/XLIFF round-trip UI.** Backend-supported; not currently exposed for export (commented out) or import (not in the allow-list). Roadmap candidate (Q-B7, Q-C3).
- **Environment migration UI.** Worker capability exists; a full self-service trigger surface is not confirmed in-repo. Roadmap candidate (Q-C4, Q-D3).
- **Module deletion.** No delete endpoint (commented out). Out of scope until decided.
- **Translator role & simplified translator experience.** Not present; roadmap candidate (Q-B1, Q-D5).
- **Human review/approval gate before publish.** Not enforced; roadmap candidate (Q-B2).
- **The external "Extension" consumer.** Referenced via "Extension Sync" notifications but not part of this repo; owner and contract undefined (Q-D4).

## 9. Open Product Questions

> These remain open because the authoritative decisions file was empty — none were resolved. Grouped by the original question ids.

**Terminology**
- **Q-A1 — Product name.** Canonical customer-facing name among **Blocks Localization / EuroLM / UILM** is undecided; and whether EuroLM/UILM should mean anything to a customer or be retired.
- **Q-A2 — Item vs. version wording.** What users should call (a) the translatable item ("key") and (b) each language's value ("resource"), so wording is consistent with the "Translations" area label.
- **Q-A3 — What a Module is.** Whole app, feature area, or organizing folder; and who decides the grouping.
- **Q-A4 — Missing-text fallback.** Is `[ KEY MISSING ]` an acceptable production fallback, or should it never reach users (e.g. fall back to default-language text)?
- **Q-A5 — "Default language" label.** Is "default language" clearer than "source/original language," and must there always be exactly one?

**Flows & UX**
- **Q-B1 — Primary user.** Who is the intended day-to-day user, and should there be a focused translator experience distinct from a project admin?
- **Q-B2 — AI review gate.** Must AI output be human-reviewed/approved before going live? Today nothing enforces it.
- **Q-B3 — Delivery path.** Is pull (JSON file) or push (webhook) the standard path; keep both; and what system does the webhook notify?
- **Q-B4 — Two publish triggers.** Should publishing always be deliberate/all-at-once, or is implicit per-module auto-publish on save acceptable (risk of surprise go-lives)?
- **Q-B5 — Two histories.** What decisions do change-history vs. export-history / generation-history support, and do they overlap?
- **Q-B6 — Glossary tiers & suggestions.** How should users build/apply global/module/key glossaries, and how much should the AI be trusted to auto-pick terms? Intended use of the glossary `Language` field is unclear.
- **Q-B7 — Import/export formats.** Which formats should be exportable/importable, and should the two lists match? (Today export UI = JSON/XLSX/CSV, import = CSV/XLSX/JSON, backend also supports XLF.)

**Business use cases & value**
- **Q-C1 — Headline problem.** The one-sentence primary value (cost reduction / more languages faster / terminology consistency / centralization).
- **Q-C2 — AI vs. professional translators.** Reduce reliance on professional translators, or give them a better starting point?
- **Q-C3 — External translation vendors.** Are outside agencies (XLIFF hand-off) an intended, supported part of the workflow, and what does a smooth hand-off require?
- **Q-C4 — Environment migration scenario.** New-environment promotion, cloning for a new customer, or other; is it self-service, and where does it live?
- **Q-C5 — Definition of "finished."** Every key in every language, or nuanced (only visible pages, only market-relevant languages)? Determines what "completeness" measures/warns about.

**Scope & boundaries**
- **Q-D1 — Self-contained data.** Should it stay self-contained or eventually share/route data through other Blocks services (e.g. blocks-data)?
- **Q-D2 — Change history ownership.** Should translation history live here permanently or roll up into platform monitoring/audit?
- **Q-D3 — Modules vs. console apps/environments.** Where is the line; should adding an app/environment in the console auto-create a module here?
- **Q-D4 — External "extension" + webhook consumers.** What outside systems consume translations this way, who owns the integration, and is it a core promise or an optional add-on?
- **Q-D5 — Roles.** Should translators get a limited role (edit/translate, not publish/delete)? Does the intended role set exist today, or must it be defined?
